# ADR 0001. 동시성 모델

- 상태: 확정 (A. 스레드 풀 + 블로킹 I/O)
- 날짜: 2026-11-20 제안, 2026-11-23 확정
- 정한 사람: 핑구 (페이즈 4 질문 지도 Q1)

## 배경

명세서는 fork, pthread, I/O 멀티플렉싱 중 하나 이상으로 동시 요청을 처리하라고 요구한다. 이번 목표는 "기본 구현 → 함수 단위로 읽기 → 리팩토링으로 학습"이다. 그래서 처음 읽을 때 흐름이 위에서 아래로 이어지는지가 중요하다.

## 선택지

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 스레드 풀 + 블로킹 I/O | 요청 하나의 처리가 함수 호출 순서대로 읽힘. 스레드 수가 고정이라 자원 사용량을 예측할 수 있음 | keep-alive 유휴 연결이 워커를 점유함 (slowloris). 공유 상태에 동기화 필요 |
| B | epoll 이벤트 루프 + 논블로킹 I/O | 유휴 연결 비용이 거의 없음. C10K 대응. 포트폴리오 가치가 가장 큼 | 연결 상태 머신, 부분 I/O, 논블로킹 connect 필요. 처리 흐름이 이벤트 단위로 쪼개져 처음 읽기 어려움. Linux 전용 (macOS는 kqueue) |
| C | fork (연결마다 프로세스) | 구현이 가장 단순. 프로세스끼리 격리됨 | 프로세스 생성 비용. Round-Robin 카운터를 프로세스 간에 공유하기 어려움 |

## 추천

A. 완화책:
- 소켓 읽기 타임아웃 5초 + 요청 전체 마감 10초 → 408
- 연결당 최대 요청 100개
- 작업 큐가 가득 차면 503

B는 리팩토링 R1로 진행한다. 파서와 응답 모듈을 순수 층으로 분리해 두었으므로, 바뀌는 범위는 thread_pool, conn, proxy로 한정된다.

## 결과

A로 확정한다. 스텝 5에서 `thread_pool`(워커 8, 작업 큐 128)과 `conn`(연결 하나의 수명, keep-alive 반복)을 만든다.

- 지금까지의 흐름(읽기 → 파싱 → 라우터 → 핸들러)을 `conn_serve` 안으로 그대로 옮길 수 있다
- 연결 하나 = 워커 하나를 끝까지 점유한다. 완화책은 위 추천과 같다
- 이후 영향: 스텝 7 프록시는 워커 안에서 블로킹으로 백엔드를 기다린다. Round-Robin 카운터는 여러 워커가 함께 올리므로 원자적 변수로 둔다
- B(epoll)는 리팩토링 R1에서 A와 wrk 처리량을 비교하며 구현한다. C(fork)는 Round-Robin 공유 문제로 고르지 않았다
