## 1. 왜 하나 (동기와 목적)
수강신청을 하면서 불편했다. 느렸고, 됐는지 몰랐고, 안 되면 계속 눌렀다. "수강신청 서버는 어떻게 만들어야 하나"가 궁금해졌다. 처음 만든 것은 그냥 **차례대로 나눠 주는** 로드 밸런싱이었다.

**목적:** 차례대로 나누는 서버를 수강신청에 맞게 **하나씩 고치면서**, 각 단계가 무엇을 낫게 하고 무엇을 나쁘게 하는지 재고, **왜 그 단계를 골랐는지** 말할 수 있게 한다.

**비중:** 신청 기간 70%, 도중 고장과 업데이트 20%, 준비 기간 10%. 신청 기간은 몰리는 유일한 때이고, 그때 실패하면 되돌릴 수 없기 때문이다(핑구 판단).

## 2. 연구 질문
| | 질문 | 왜 궁금한가 |
|---|---|---|
| **R1** | 차례대로 나누는 서버는 신청 기간에 어디서 무너지나 | 고칠 곳을 알려면 무너지는 곳부터 봐야 한다 |
| **R2** | 요청과 상황에 따라 다르게 다루면 얼마나 나아지나 | "요청이나 처리에 따라 다른 분배를 해야 하지 않을까" |
| **R3** | 우선순위는 사람이 많아져도 지켜지나 | 동시에 눌러도 먼저 온 사람이 먼저여야 한다 |
| **R4** | 만 명이 동시에 와도 견디나. 안 되면 무엇이 막나 | "만 개 되나?" |

## 3. 지금까지 아는 것
모두 같은 컴퓨터(2코어)에서 잰 값이다. 자세한 표는 [보고서](report-traffic.md).

| 질문 | 아는 것 |
|---|---|
| R1 | 신청 100명(용량의 3.3배)에서 성공 25~26명. 신청이 100개 몰리면 화면이 1.2초 걸리고, 500개면 화면 성공 1/737 |
| R2 | 준비 기간 조회 p99 2.0초 → 0.014초(덜 바쁜 쪽). 한 대가 바로 500이면 덜 바쁜 쪽만 쓰면 실패 90%, 빼기를 켜면 0.1% |
| R3 | 얌전한 학생 100명에서는 처음도 지금도 먼저 온 순서를 지킨다. 계속 누르는 학생이 섞이면 줄을 짧게 한 방법은 얌전 50%, 계속 누름 100%. 번호표(자리 12)는 79~82% 대 88% |
| R4 | 대기 줄을 128에서 2048로 키우면 동시 500명에서 신청 성공 3명 → 321명, 화면 163/257 → 293/293. 2,000명까지 화면이 산다(신청 성공은 321 → 247 → 178명으로 준다). **만 명은 아직 안 쟀다.** 정적 파일은 동시 연결 5,000 · 10,000에서 응답의 73% · 89%가 503이다(워커 8, 줄 4096) |

**백엔드 한 대도 여러 일을 동시에 한다.** 처리 스레드 수가 곧 동시 처리 수다. 100ms짜리 신청을 스레드 8개면 초당 74건, 128개면 1,236건, 256개면 2,437건까지 재었다(이론 80 · 1,280 · 2,560). 그래서 신청은 백엔드를 늘리기 전에 **프록시의 워커와 줄이 먼저 막힌다.** 워커는 설정 상한이 256이라 프록시 한 대는 초당 약 2,560건이 천장이다(계산).

## 4. 연구 · 테스트 · 실험을 구분하기
| | 목적 | 답이 어떤 모양인가 |
|---|---|---|
| **테스트** | 만든 것이 맞게 동작하나 | 통과 / 실패 |
| **실험** | 두 방법 중 무엇이 나은가. 가설을 세우고 비교한다 | A가 B보다 얼마나 낫고, 언제 지는가 |
| **연구** | 어디까지 되고 왜 멈추나. 답을 모르고 시작한다 | 한계 값과 원인 |

하나의 작업에 하나의 목적만 둔다. 목적이 다르면 따로 적는다.

## 6. 설계

### 6.1 흐름
```
학생 ─▶ 받기(accept) ─▶ 대기 줄(크게) ─▶ 워커 (요청을 읽음) ─▶ 번호표 줄 ─▶ 고르기 ─▶ 백엔드 1 · 2 · 3
                          │                               │              │
                          넘치면 503                      앞에 자리만큼만 봄   덜 바쁜 쪽 + 빼기
```

### 6.2 새로 만들거나 바꿀 것
| | 바꾸는 것 | 이유 | 크기 [예측] |
|---|---|---|---|
| 가 | 줄 크기 기본값 128 → 2048 (설정) | 동시 500~2,000에서 번호표를 가진 학생이 자리를 잃지 않는 것을 쟀다 | 한 줄 |
| 나 | 번호표 안에 순서를 넣고, 앞사람은 **줄 맨 앞부터 자리 수만큼만** 본다 | 지금은 목록 전체(2,048칸)를 락 안에서 훑고, 2,049번째 학생은 번호표를 못 받는다 | 120줄 |
| 다 | 번호표 장수 상한 2,048 → 16,384 | 만 명 목표 | 한 줄 + 나 |
| 라 | 만 명 부하를 만드는 측정 도구 | 얌전한 학생은 1초에 한 번 온다(wrk의 `delay()`), 번호표를 잃지 않는다 | 60줄 |

결정이 필요한 두 가지는 [Q9 질문 지도](question-maps/Q9-대량신청.md)의 결정 카드에 있다: **번호표 목록을 빠르게 하는 방법(추천 A)** 과 **줄이 넘쳤을 때(추천 B)**.

### 6.3 하지 않는 것과 이유
- **문(번호표 검사)을 워커 앞으로 옮기기:** 큰 구조 변경이다. 큰 대기 줄로 2,000명까지 됐으므로 만 명에서 막힐 때만 연다
- **백엔드 여러 대 더:** 신청은 프록시가 먼저 막힌다(3장). 백엔드는 스레드를 늘려서 본다
- **CGI · 포워드 프록시 · DB 좌석:** 나눌 수 없음 · 방향이 반대 · 범위 밖. 이유는 보고서 7장

## 8. 한계와 말하지 않을 것
- "만 명을 견딘다"고 먼저 말하지 않는다. S1의 값으로만 말한다
- 같은 컴퓨터 안의 실험이다. 컴퓨터가 꺼지거나 네트워크가 끊기는 것은 재지 않았다
- 좌석의 주인은 DB가 정한다. 우리 실험에는 DB가 없다
- 덜 바쁜 쪽 · 빼기 · 번호표는 알려진 방법이다. 발명이라고 하지 않는다. 우리 것은 **재고 고른 과정**이다
- 앞 판에서 틀린 것(두 번 처리 0명, 고르게 나누기, 예측들)은 보고서에 정정해 두었다
