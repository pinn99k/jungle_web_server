## 1. 무엇을 풀려 하나
수강신청 시스템은 1년 내내 같은 모습이 아니다. 평소에는 시간표만 보고, 신청 날 아침에는 모두가 같은 버튼을 누르고, 신청 중에도 서버를 고쳐야 할 때가 있다.

서버를 3대 두었다. 그런데 **지금 프록시는 1년 내내 똑같이 동작한다.** 차례대로 나눠 주고, 조회와 신청을 구분하지 않고, 모두 같은 시간만큼 기다린다.

> 질문: 학사 일정의 때마다 무엇을 다르게 해야 하나? 그 방법은 언제 틀리나?

## 2. 학사 일정으로 본 상황 여섯 가지

| # | 때 | 무슨 일이 벌어지나 | 학생이 바라는 것 |
|---|---|---|---|
| 1 | **평소 (신청 기간 아님)** | 시간표 조회만 드문드문. 3대가 모두 한가하다 | 바로 뜨는 화면 |
| 2 | **신청 전 준비 기간** | 강의계획서와 성적 통계를 많이 본다. 통계는 한 번에 오래 걸린다 | 남이 통계를 봐도 내 조회는 빨리 |
| 3 | **신청 시작 순간** | 정각에 모두가 신청을 누른다. 안 되면 새로고침한다 | 됐는지 안 됐는지 확실히. 공평하게 |
| 4 | **신청 도중 서버 한 대 고장** | 누르고 있던 신청의 결과를 모르게 된다 | 두 번 신청되지 않기. 안 된 줄 알고 포기하지 않기 |
| 5 | **신청 기간에 업데이트** | 세 대를 하나씩 새 버전으로 바꾼다. 막 켜진 서버는 아직 느리다 | 업데이트 중인 줄 모르기 |
| 6 | **업데이트 실수** | 새 버전이 켜졌는데 요청을 받자마자 오류를 낸다 | 멀쩡한 서버로 안내받기 |

## 3. 상황마다 무엇을 고민하나
"나쁜 일"이 때마다 다르다. 이것이 방법을 고르는 기준이다.

### 상황 1. 평소, 조회만 있다
- 가장 나쁜 일: 서버 3대를 켜 두고 노는 것. 학생 입장에서는 느린 화면
- 고민: 이때도 3대가 다 필요한가? 몇 대를 꺼도 학생이 모르나?
- 방법 후보: 3대 모두 / 한 대만 켜기 / 두 대
- 풀리는 궁금증: "서버가 몇 대여야 의미가 있나"

### 상황 2. 준비 기간, 무거운 요청이 섞인다
- 가장 나쁜 일: 통계를 보는 한 학생 때문에 다른 학생의 조회가 멈추는 것
- 고민: 차례대로 나누면 한 서버가 통계에 붙잡힌 사이 그 뒤의 조회가 기다린다. 덜 바쁜 쪽으로 보내면? 통계만 따로 자리를 주면?
- 방법 후보: 차례대로 / 덜 바쁜 쪽 / 통계 자리를 따로 두기
- 풀리는 궁금증: "로드 밸런서는 그냥 차례대로 아닌가", "백엔드마다 응답 시간이 다르면"

### 상황 3. 신청 시작 순간 (깊게 파는 상황)
- 핑구의 질문: **동시에 누르면 누가 먼저인가? 그건 백엔드의 문제인가 웹서버의 문제인가?**
- 가장 나쁜 일: 얌전히 기다린 학생이 계속 누른 학생에게 자리를 뺏기는 것

누가 무엇을 정하나:

| | 웹서버가 할 수 있나 | 근거 |
|---|---|---|
| 먼저 **누른** 학생을 알아보기 | 못 한다 | 도착 순서만 보인다. 손님 쪽에서 이미 4~5% 뒤집힌다 |
| 먼저 **도착한** 학생부터 들이기 | 한다 | 줄이 그렇게 한다 |
| 다시 눌러도 유리하지 않게 | 한다 | 지금은 얌전한 학생 62%, 계속 누르는 학생 74% |
| 떠난 학생의 자리를 다음 사람에게 | 한다 | 핑구의 규칙 (2026-11-25): 떠났으면 다음 사람 것 |
| 마지막 좌석을 한 명에게만 | 못 한다 (백엔드 · DB) | 이번 범위 밖 |

- 로드 밸런서의 "공정한 분배"(서버마다 고르게)와 학생의 공정함(먼저 온 사람 먼저)은 다른 말이다
- "떠남"을 볼 방법이 없어서 **몇 초 동안 소식이 없으면 떠난 것으로 본다**. 이 몇 초(유예)가 재야 하는 값이다: 길면 빈 자리가 놀고, 짧으면 잠깐 끊긴 학생이 억울하다
- 방법 후보: A 지금(기억 없음) / B 줄 서기(번호표로 기억, 유예 시간을 바꿔 가며) / C 추첨 순서
- 줄 서기의 모양: 처음 오면 웹서버가 **추측할 수 없는 번호표**(쿠키)를 준다. 자리가 없으면 거절하고, 같은 번호표로 다시 오면 **같은 순서**다. 웹서버는 학번 · 세션 · 토큰을 보지 않으므로 서비스가 어느 방식이어도 된다. 로그인과 신청 자격은 백엔드가 판단한다. 기다리는 동안 연결과 워커를 붙잡지 않는다
- 한계: 번호표는 사람이 아니라 표를 기억한다. 한 학생이 번호표를 여러 장 받으면(탭 여러 개) 자리도 여러 개다. 막으려면 누구인지 알아야 하고 그건 백엔드의 일이다
- 잴 것: 얌전한 학생과 계속 누르는 학생의 성공률 차이, 번호표를 여러 장 받은 학생의 이득, 유예 시간에 따른 빈 자리와 억울한 학생, 두 번 신청

### 상황 4. 신청 도중 서버 한 대 고장
- 가장 나쁜 일: 같은 신청이 두 번 되거나, 됐는데 안 된 줄 아는 것
- 고민: 처리 중이던 신청은 됐을까? 다른 서버에 다시 보내면 두 번 될 수 있고, 안 보내면 실패로 보인다. 조회는 다시 보내도 된다
- 방법 후보: 다시 안 보냄 / 조회만 다시 보냄 / 모두 다시 보냄. 그리고 고장 난 서버의 몫을 어디로 보내나(옆 한 대에 몰기 / 고르게)
- 풀리는 궁금증: "보조가 이어받으면 처리 중이던 일은", "요청 쪽이 궁금하다"

### 상황 5. 신청 기간에 업데이트
- 가장 나쁜 일: 학생이 "접속이 안 돼요"를 보거나, 막 켜진 서버에 몰려 느려지는 것
- 고민: 막 켜진 서버는 일이 없어 한가해 보인다. 그래서 몰아 주면 준비가 덜 된 서버가 쓰러진다. 천천히 늘리면?
- 방법 후보: 차례대로 / 덜 바쁜 쪽 / 천천히 늘리기
- 풀리는 궁금증: "새 서버로 몰리는 것이 진짜인가"

### 상황 6. 업데이트 실수
- 가장 나쁜 일: 틀린 서버가 가장 한가해 보여 손님이 그리로 몰리는 것
- 고민: 상황 2에서 이긴 방법이 여기서는 독이 될 수 있나? 프록시가 "이 서버는 이상하다"를 어떤 신호로 아나?
- 방법 후보: 차례대로 / 상황 2에서 고른 방법 / 이상한 서버를 잠깐 빼기
- 풀리는 궁금증: "방법이 서버 쪽에만 있다"는 지적. 여기서는 응답의 내용까지 봐야 안다

**여섯 상황은 순서대로 이어진다.** 앞에서 고른 방법을 다음 상황에서 다시 시험해, 어디서 틀리는지 본다.

## 5. 실험이 유의미한지 점검
결과가 어느 쪽으로 나와도 배우는 것이 있나로 걸렀다.

| 상황 | 뻔한가 | 그래도 하는 이유 | 어떤 결과면 놀라운가 |
|---|---|---|---|
| 1 평소 | 중간 | "3대가 항상 필요한가"에 답하려면 1대로도 재야 한다 | 1대로 조회가 느려지면 |
| 2 준비 기간 | 중간 (덜 바쁜 쪽이 낫다고 알려짐) | 얼마나 나은지, 어디서 뒤집히는지는 모른다 | 차례대로와 차이가 작으면 |
| 3 신청 시작 | 중간 (짧은 줄이 낫다는 건 이미 잼) | 자리 나누기가 더 나은지는 안 잼 | 나누는 게 더 나쁘면 |
| 4 고장 | 낮음 | 조회는 얻고 신청은 잃는 양을 모른다 | 다시 보내도 두 번 신청이 거의 없으면 |
| 5 업데이트 | **낮음** | 통설을 확인한다 | 몰리지 않으면 |
| 6 업데이트 실수 | **낮음** | 2에서 이긴 방법을 뒤집을 수 있다 | 덜 바쁜 쪽이 오히려 나으면 |

그만둘 기준: 같은 조건을 5번 반복한 흔들림보다 차이가 작으면 "차이 없음"으로 적고 더 파지 않는다. 새 방법을 만들었다고 말하지 않는다. 방법은 알려진 것이고, 우리 것은 **우리 상황에서 잰 결과와 고른 이유**다.

## 6. CGI를 왜 쓰지 않았나
- **원래 구현하는 것인가:** 명세는 동적 처리의 예로 "CGI 프로그램 실행, **또는** 백엔드 서버로 요청 전달"을 들었다. 둘 중 하나면 된다
- **실무에서는:** 요청마다 프로그램을 띄우는 순수 CGI는 드물어졌다. 켜 둔 프로그램을 재사용하는 방식(FastCGI)이나 앱 서버로 HTTP를 전달하는 방식을 주로 쓴다. `git http-backend`처럼 아직 쓰는 것도 있다
- **우리가 안 쓴 가장 큰 이유:** CGI는 프록시가 있는 컴퓨터에서 돈다. 서버 3대로 나눌 수가 없다. 신청 시작 순간(상황 3)이나 고장(상황 4)을 나눠 감당하려는 우리 서비스와 반대 방향이다
- **두 번째 이유:** 요청마다 처음부터 시작해 DB 연결 같은 상태를 매번 다시 맺는다
- **느려서가 아니다:** 생성 비용을 재니 0.66~1.96ms다. 신청이 100ms라 거의 안 보인다
- **구현한다면 어떤 때인가:** 다른 언어로 만든 작은 프로그램을 붙일 때, 가끔 부르는 관리 작업, 자주 죽는 프로그램을 따로 가두고 싶을 때. 성적 통계가 **아주 드물고 프록시와 같은 컴퓨터에서 돌아도 된다면** 후보가 될 수 있다
- **이번 결정:** 넣지 않는다. 여섯 상황이 끝난 뒤 시간이 남으면 비교용으로 다시 본다

## 7. 어떻게 재나
- 상황마다 "학생이 겪는 것"으로 잰다: 조회가 뜨기까지, 신청 성공률, 두 번 된 신청, 됐는데 안 된 줄 안 신청
- 같은 조건을 5번 반복하고 범위를 적는다. 한 번만 잰 값은 그렇게 표시한다
- 부하는 curl과 wrk만 쓴다 (ADR 0002). 막히는 상황은 손님을 정해진 속도로 보낸다 (답을 기다렸다 보내는 도구는 막히는 상황을 실제보다 좋게 보인다)
- 예측은 재기 전에 적고 잰 뒤에 고치지 않는다 (부록)
- 전체 측정은 90분을 넘기지 않는다. 넘으면 줄이고, 줄인 사실을 적는다

## 9. 한계
- 한 컴퓨터 안의 3대다. 컴퓨터가 꺼지거나 네트워크가 끊기는 것은 재지 않는다
- 요청의 비율과 걸리는 시간은 가정이다. 결론은 조건과 함께 적는다
- 실제 학교의 시스템을 관찰한 것이 아니라 상황을 가정한 것이다. 실제 운영과 다를 수 있다

## 10. 보고서 모양
상황마다 한 쪽: 어느 때인가 → 예측(누가 무엇을) → 방법 후보 → 잰 결과 → 맞았나, 틀렸으면 왜 → 고른 방법과 이유 → **이 방법이 지는 때**. 마지막 장에 "수강신청 1년 운영표"를 붙인다: 학사 일정의 때마다 무엇을 켜고 무엇을 끄나.

## 11. 승인받을 것
1. **공유 상태 추가:** 서버별 처리 중 개수와 아픈 시각을 원자적 변수로 둔다 (CLAUDE.md의 "전역 가변 상태는 둘뿐" 규칙을 바꾼다). 락은 쓰지 않는다
2. **설정 키 추가:** 줄 길이, 고르는 방법, 빼는 시간, 종류별 자리
3. **CGI는 이번에 넣지 않는다**
   - 줄 서기에는 여러 값을 함께 바꾸는 목록이 필요해 **락 하나**를 쓴다 (원자적 변수로는 안 된다). 한계: 프록시가 죽으면 줄도 사라진다
4. **때마다 가장 나쁜 일** (3장에 제안을 적었다. 핑구가 고치면 결론이 달라진다)
5. **커밋:** 스텝마다 커밋. push는 핑구. 지금까지 쌓인 변경도 먼저 커밋하며 핑구의 메모(`main.c`, `static_handler.c`)가 함께 들어간다

## 12. 부록: 재기 위한 조건과 미리 적은 예측
상황을 재려면 숫자가 필요하다. 이 숫자는 **결론이 아니라 조건**이다.

| 상황 | 재는 조건 | Claude 예측 (재기 전) | 핑구 예측 |
|---|---|---|---|
| 1 평소 | 조회만, 천천히. 서버 1 · 2 · 3대 | 1대와 3대의 조회 시간 차이가 거의 없다 | |
| 2 준비 기간 | 통계(2초) 5%가 섞임 | 조회 p99: 차례대로 약 2초, 덜 바쁜 쪽 0.1~0.3초 | |
| 3 신청 시작 | 얌전한 · 계속 누르는 · 잠깐 끊긴 · 떠난 학생이 섞임, 용량보다 많이 | 줄 서기를 켜면 두 학생의 성공률 차이가 5%p 안으로 줄고, 유예가 길수록 빈 자리가 늘어난다 | 떠났으면 다음 사람 것 (2026-11-25) |
| 4 고장 | 초당 25명, 서버 하나가 처리 중에 죽음 | 고르게 나누면 성공 약 78~80%. 모두 다시 보내면 두 번 신청이 생김 | |
| 5 업데이트 | 한 대가 켜진 뒤 5초 동안 10배 느림 | 덜 바쁜 쪽은 저절로 피한다. 통설은 요청이 짧을 때만 보인다. 확신 낮음 | |
| 6 업데이트 실수 | 한 대가 받자마자 오류 | 차례대로 실패 33%, 덜 바쁜 쪽 60~90%, 빼기는 첫 몇 건 뒤 0% | 차례대로가 실패가 더 많다 (2026-11-25) |

1판에 적었던 예측 중 상황과 짝이 되는 것은 숫자를 그대로 옮겼다. 상황 1의 예측은 이번에 새로 적었다.
